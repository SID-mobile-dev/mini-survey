## 1. Выбранный AI-setup

| Компонент | Значение |
|-----------|----------|
| IDE / редактор | Проект открыт в JetBrains IDE (PyCharm, по `.idea/` и Python-модулю), но ИИ-функционал IDE не использовался |
| Ассистент / агент | **OpenCode** — агент-харнесс в терминале (TUI/CLI): самостоятельно читает и пишет файлы, выполняет команды, работает по шагам с подтверждением |
| Модель | **MiMo v2.6 Pro** (`xiaomi/mimo-v2.6-pro`, Xiaomi) — основная модель для генерации и отладки |
| Провайдер | Кастомный OpenAI-совместимый провайдер `@ai-sdk/openai-compatible` с `baseURL` от Xiaomi MiMo API (ключ в `~/.config/opencode/opencode.json`, в отчёт не включён) |
| Плагины | Не использовались |
| Прочее | Доступна вторая модель того же провайдера (`mimo-v2.6-flash`) — в работе не участвовала |

### Как настроено

- Конфигурация OpenCode — глобальная (`~/.config/opencode/opencode.json`): подключение провайдера MiMo и двух моделей. Проектного конфига `opencode.json` нет — работа идёт с настройками по умолчанию.
- Режим работы: интерактивный диалог с агентом. Агенту делегировано всё — от структуры проекта до запуска и скриншотов; человек ставит задачи, подтверждает шаги и правит поведение модели.
- Дисциплина работы: каждый шаг плана запускается отдельным подтверждением человека, по ходу пишется этот отчёт.
- Версии окружения: Python 3.15.2, macOS. Node.js в окружении отсутствует — но для выбранного стека (FastAPI + HTML/JS) он и не нужен.

## 2. Рассмотренные альтернативы

| Альтернатива | Почему рассматривалась | Почему не выбрана |
|--------------|------------------------|-------------------|
| **Cursor** | Полноценная IDE с встроенным ИИ-агентом, автокомплит и чат прямо в редакторе | Отдельный форк IDE вместо привычного редактора; подписка за полный функционал; хотелось проверить именно «агент в терминале», а не «ИИ внутри IDE» |
| **GitHub Copilot** | Встроен в популярные IDE, привычный помощник в коде, хорошая подсказка на лету | Скорее автокомплит/чат, чем автономный агент: слабее в многошаговых задачах («сгенерируй проект целиком, запусти, почини»), которые и составляют суть ДЗ |
| **Claude Code** | Сильный терминальный агент, ближайший конкурент выбранного формата | Хотелось опробовать менее раскрученный инструмент и сравнить; к тому же доступ к модели уже был настроен через OpenCode |

**Итоговый выбор — OpenCode + MiMo v2.6 Pro**: формат «агент делает всё сам» (файлы, команды, запуск) — ровно то, что нужно для максимального делегирования; работа идёт в терминале, не привязывая к конкретной IDE.

### 0. Предыстория: стартовый скелет (другая сессия с ИИ)

Структура проекта `backend/` + `frontend/` с файлами-заглушками была создана **4 ноября в прошлой сессии с ИИ** (другой инструмент). ### 3. Генерация backend (шаг 3 ДЗ)

**Промпт пользователя:**

> начинай шаг 3

*(Работа строится по шагам плана, каждый шаг человек запускает отдельной командой; план шага — генерация backend по файлам — был согласован агентом в предыдущем сообщении и подтверждён этим промптом.)*

**Что делал агент — генерация по одному файлу за раз:**

1. `backend/app/questions.py` — список из 4 жёстко заданных вопросов (id, text, type: `text`/`textarea`), функция `get_questions()`.
2. `backend/app/storage.py` — in-memory хранение: список `_answers`, функции `save_answers()`, `get_all_answers()`, `clear()`.
3. `backend/app/main.py` — FastAPI: `GET /questions`, `POST /answers` с валидацией (Pydantic-модели), служебный `GET /api/answers` для проверки, раздача `frontend/` через `StaticFiles` (mount последним, чтобы статика не перехватывала API), CORS для локальной разработки.
4. Окружение: venv в `backend/.venv`, `pip install -r requirements.txt` (FastAPI 0.163.1, uvicorn 0.54.0, pydantic 2.14.3).

**Smoke-тест (curl):**

| Проверка | Результат |
|----------|-----------|
| `GET /questions` | 200, 4 вопроса с корректными кириллицей и типами |
| `POST /answers` (4 ответа) | `{"status":"ok","saved":1}`, данные в памяти |
| `GET /api/answers` | сохранённый набор виден целиком |
| `GET /` (фронтенд) | 200, статика раздаётся |
| `POST /answers` c `question_id: 99` | 422 `{"detail":"Неизвестный вопрос: id=99"}` |
| `POST /answers` c пустым списком | 422, внятная ошибка валидации Pydantic |
| `POST /answers` с пустым `value` | 422 `string_too_short` |

Backend поднялся и прошёл все проверки **с первого раза**. Честное наблюдение: неудачных попыток на этом шаге не было — задача типовая, и модель сразу сгенерировала рабочий код. Это важно для отчёта: сильная сторона инструмента — скорость на стандартных CRUD-задачах.

**Реальная ошибка модели на этом шаге** (не в коде, а в тексте отчёта): при генерации таблицы альтернатив в русский текст затесался фрагмент на другом языке («встроен в主流 IDE» вместо «встроен в популярные IDE»). Ошибка обнаружилась при перечитывании и правилась отдельным действием. Вывод: языковые «смешения» — характерный артефакт генерации, за итоговым текстом нужно перечитывать.

### 4. Генерация frontend (шаг 4 ДЗ)

**Промпт пользователя:**

> начинай

*(Короткая «команда на запуск шага»: детали — форма, загрузка вопросов, отправка, «Спасибо!» — были описаны агентом в плане шага и подтверждены промптом. Человек работает в режиме «подтверждаю — выполняй», не переписывая задачу заново.)*

**Что делал агент — генерация по одному файлу за раз:**

1. `frontend/index.html` — два экрана в разметке: форма (`#survey-view`) и «Спасибо!» (`#thanks-view`), контейнер `#questions` для вопросов, блоки загрузки и ошибок.
2. `frontend/app.js` — `loadQuestions()` через `fetch GET /questions`, динамический рендер полей (по `type` вопроса: `text` → однострочное поле, `textarea` → многострочное), клиентская проверка заполненности, `POST /answers` с `{answers: [{question_id, value}]}`, переключение на экран «Спасибо!», кнопка «Пройти ещё раз», обработка ошибок сети/валидации с показом сообщения пользователю.
3. `frontend/style.css` — карточка по центру, стилизованные поля, состояния фокуса/ошибки/заблокированной кнопки, зелёный экран «Спасибо!».

**Решения, принятые по ходу:**

- API-база пустая (`API_BASE = ""`): backend раздаёт фронтенд с того же порта, относительных путей достаточно; CORS на backend остаётся как подстраховка для открытия через `file://`.
- Оба типа вопросов (`text`/`textarea`) рендерятся `<textarea>`: для `text` — одна строка. Упрощение против `<input>`, зато одинаковая логика сбора ответов.
- Пустые поля ловятся на клиенте до отправки, но сервер остаётся источником истины (серверная валидация не отменялась).

**Проверка после генерации:** `GET /` отдаёт `index.html`, `app.js` и `style.css` — 200. Полный сценарий в браузере — следующий шаг.

**Наблюдение:** неудачных попыток нет и здесь — генерация типового фронтенда (fetch + форма + два экрана) тоже попадает с первого раза. Почти вся «настройка поведения модели» в этом ДЗ свелась не к правкам кода, а к организации процесса: пошаговые подтверждения, ведение отчёта, контроль перечитыванием.

**Неудачные попытки этого шага (реальные, фиксирую честно):**

1. **Ошибка в аргументах вызова инструмента.** Заполнение формы через `fill_form` не прошло с первого раза: вызов был сделан с полями `{ref, value}`, а API требует явного типа (`{type: "text", ref, value}`). Ошибка вернулась понятной схемой, правка — одна минута. Наблюдение: даже у «агентного» инструмента свои точные сигнатуры вызовов, и модель их не всегда угадывает; хорошая новость — ошибки самодокументируемы и правятся на лету.

2. **Скриншоты через встроенный браузер не сработали.** `browser.screenshot` трижды вернул «Screenshot needs a visible tab», включая повторы после того, как окно приложения было открыто вручную. Таб был в фокусе, страница — рабочая; отказ именно на этапе захвата пикселей. Диалог с инструментом по этой проблеме:

## 4. Впечатления и мысли

**Что понравилось и ускоряло работу:**

- **Скорость на типовых задачах.** Backend и frontend были сгенерированы мгновенно и заработали с первого раза: все curl-тесты, включая валидацию ошибок, — зелёные сразу. На «стандартных» CRUD-паттернах инструмент экономит часы.
- **Полное делегирование.** Агент сам писал файлы, создавал venv, ставил зависимости, поднимал сервер, прогонял сценарий в браузере и проверял данные на backend. Человек ставил задачи и подтверждал шаги — ровно тот рабочий цикл, который и хотелось опробовать.
- **Коротких команд хватает.** Благодаря удержанию контекста для запуска шага хватало слов «начинай» — план шага агент помнил и проговаривал его перед выполнением.
- **Ошибки самодокументируемы.** Промах с сигнатурой `fill_form` вернулся понятной схемой: правка — одно действие, без гугления и чтения доков.
- **Отчёт пишется по ходу.** Агент фиксировал промпты и наблюдения в `REPORT.md` параллельно работе — к финалу не пришлось восстанавливать историю по памяти.
- **Вопросы вместо додумывания.** По инструкции «не выдумывай ответы» агент задавал уточняющие вопросы (стек, setup, способ скриншотов) — это сэкономило время и уберегло от лишних переделок.

**Что мешало или разочаровало:**

- **Визуальная проверка — слабое место.** Скриншоты через встроенный браузер не заработали ни после повторов, ни после ручного открытия окна. Для задач, где важно «как выглядит», инструмент пока уступает IDE-инструментам с живым превью.
- **Сгенерированный текст нужно перечитывать.** В русский текст отчёта затесался фрагмент на другом языке (иероглиф вместо слова) — тихая ошибка, которую видно только при перечитывании.
- **Точные сигнатуры внутренних инструментов модель угадывает не всегда** — приходится полагаться на сообщения об ошибках.
- **История работы не переносится между инструментами.** Промпты прошлой сессии (другой инструмент) утеряны безвозвратно — об этом ниже.

## 5. Возникшие проблемы

1. **Потеря истории промптов при смене инструмента.** Скелет проекта делался в другой сессии (другой инструмент); извлечь тексты тех промптов автоматически не удалось (база OpenCode хранит только сессии новее 4 ноября). Обходной путь: зафиксировать факт потери честно в отчёте. Урок: вести отчёт нужно по ходу, внутри одного инструмента.

2. **Скриншоты через встроенный браузер не работают** (`Screenshot needs a visible tab`): три попытки, включая повтор после ручного открытия окна приложения. Обход: скриншоты сняты вручную; проверка сценария выполнена через accessibility-снапшоты. Это ограничение инструмента, а не приложения.

3. **Ошибка модели в генерируемом тексте:** языковое «смешение» (иероглиф в русском предложении). Обход: перечитывание сгенерированного текста и точечная правка. Кода не коснулось, но привычка перепроверять итоговый текст закрепилась.

4. **Промах модели в сигнатуре вызова инструмента** (`fill_form` без явного `type` поля). Обход: чтение сообщения об ошибке и повторный вызов. Потеря времени — меньше минуты.

5. **Изоляция code-mode:** изнутри скриптов недоступен `shell` (и вообще прямой доступ к системе — только явно перечисленные инструменты). Обход: `fetch` для HTTP-проверок. Ограничение осмысленное (безопасность), но требует привыкания.

## 6. Вывод

**Подтверждаю свой выбор: OpenCode + MiMo v2.6 Pro.**

На этой задаче инструмент показал именно то, что от него требовалось: максимальное делегирование полного цикла (генерация → запуск → проверка → отладка), скорость на типовых задачах (backend и frontend — с первого раза), понятные ошибки и нормальную работу в режиме итераций «подтвердил шаг — выполнил».

Оговорки, зафиксированные честно:

- для задач с тяжёлой **визуальной** составляющей (пиксель-перфект вёрстка, дизайн) я бы держал в уме **Cursor** как альтернативу — живое превью в IDE там сильнее;
- за сгенерированным текстом (доки, отчёты) нужно перечитывание — тихие языковые ошибки случаются;
- историю промптов стоит вести внутри одного инструмента — при смене инструмента она теряется.

Смены инструмента по ходу ДЗ не потребовалось: тот, что был выбран стартово, с задачей справился. Итоговая оценка — **выбор подтверждён, с оговорками выше, которые касаются нишевых сценариев, а не основного рабочего цикла.**
